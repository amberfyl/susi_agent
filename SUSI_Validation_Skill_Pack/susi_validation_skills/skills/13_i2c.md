# Skill: Validate I2C — Semi-Automated Flow

## Scope

Validate `[I2C]` using:
- PowerShell runner
- C# wrapper (P/Invoke to `Susi4.dll`)
- Capability gate + known-register transaction tests
- Optional approved write/read-back/restore
- Error/recovery checks

I2C full validation depends on golden device/register definitions. Without those, do not hard-fail blindly.

## Objective

Verify all required I2C behaviors:
1. Declared I2C channels are exposed by API capability
2. Known valid read transaction succeeds with correct length/data shape
3. Approved write path (if allowed) can read back and restore
4. Error handling is correct (invalid channel/address/len/timeout)
5. Bus remains usable after error/recovery path

---

## Required Inputs

### A) Platform/Test metadata
- `platform_name`
- `bios_version` (optional)
- `driver_version` / `dll_version` (optional)

### B) Channel policy
- `required_i2c_channels`
- `i2c_channel_map` (logical channel->API channel id)

### C) Golden transaction profile (per channel)
- `slave_addr_7bit`
- `register_addr`
- `register_addr_width` (8/16...)
- `read_length`
- `expected_value` or `expected_range`
- `requires_repeated_start` (true/false)

### D) Optional write policy
- `allow_write` (true/false)
- `approved_writable_register`
- `write_mask`
- `restore_required` (true)

### E) Timing/recovery policy
- `timeout_ms`
- `retry_count`
- `bus_recovery_method` (if available)

---

## Missing Conditions (do not hard-fail)

- No golden profile for required channel -> `BLOCKED_REFERENCE`
- No approved writable register but write requested -> `BLOCKED_PARAMETER`
- Fixture/device absent/unpowered -> `BLOCKED_FIXTURE`

---

## Step 0 — Probe Gate (Mandatory)

1. Initialize SUSI library
2. Query I2C capability mask (e.g., I2C supported bitmask)
3. Validate required channels are supported

Decision rules:
- required channel unsupported -> `FAIL_CAPABILITY`
- channel supported but no golden transaction data -> `BLOCKED_REFERENCE`

---

## Automated Test Flow

## Case A — Capability & Channel Mapping

Goal: verify channel support and mapping correctness.

Steps:
1. Read capability mask
2. Compare against required channel list
3. Log supported/unsupported channels

Pass criteria:
- required channels supported

Fail mapping:
- unsupported required channel -> `FAIL_CAPABILITY`
- capability API error -> `FAIL_API`

## Case B — Known Register Read (Core)

Goal: prove real transaction on intended channel/device.

Steps:
1. Execute configured read or write-read transaction
2. Verify API success and returned length
3. Compare data with expected value/range
4. Repeat N times for stability

Pass criteria:
- success rate meets policy
- returned length correct
- value/range check passes

Fail mapping:
- transaction error -> `FAIL_API`
- length mismatch -> `FAIL_READBACK`
- value mismatch -> `FAIL_FUNCTIONAL`

## Case C — Approved Write / Read-back / Restore (Optional)

Run only when `allow_write=true` and register is approved.

Goal: verify safe write path and non-destructive restore.

Steps:
1. Read original register value
2. Modify only allowed bits by `write_mask`
3. Write test value
4. Read back and compare
5. In finally: restore original value and verify

Pass criteria:
- write/read-back coherent
- restore verified

Fail mapping:
- write/read error -> `FAIL_API`
- read-back mismatch -> `FAIL_READBACK`
- restore failure -> `ABORTED_RESTORE_FAILURE`

## Case D — Error Handling & Recovery

Goal: verify invalid operations are rejected and bus recovers.

Negative scenarios:
- invalid channel
- invalid address (NACK)
- invalid length
- timeout simulation/path

Steps:
1. Run negative scenario calls
2. Verify expected error statuses
3. Run one known-good transaction after errors

Pass criteria:
- errors classified correctly
- post-error known-good transaction succeeds

Fail mapping:
- invalid call unexpectedly success -> `FAIL_API`
- bus unusable after error -> `FAIL_RECOVERY`

## Case E — Stress (Optional)

Goal: reliability under repeated transactions.

Steps:
1. Repeat known-good transaction M times
2. Track success rate/timeout rate/mismatch rate

Pass criteria:
- reliability metrics above policy threshold

Fail mapping:
- excessive timeout/mismatch -> `FAIL_FUNCTIONAL` or `FAIL_RECOVERY`

---

## L1~L6 Mapping (I2C)

- L1 Configuration: channel/golden profile/timing params complete
- L2 Capability: required channels exposed
- L3 API Command: read/write transaction statuses
- L4 Read-back: length/data/restore consistency
- L5 Functional: known device/register correctness under expected behavior
- L6 Recovery: bus usability after error/recovery paths

---

## Human Discussion Pack (for blocked/fail)

Include:
1. Missing golden profile details (addr/reg/len/expected)
2. Device presence/power status
3. Write safety decision (approved register/mask)
4. Recovery mechanism availability
5. Decision: accept read-only/API-level coverage or require write+functional coverage

## Platform Verdict Contribution

I2C verdict:
- `PASS`: required cases pass
- `CONDITIONAL`: capability/API pass but golden reference missing for full functional proof
- `FAIL`: any required case fails
- `ABORTED`: restore/recovery safety failed

Always separate `BLOCKED_REFERENCE`/`BLOCKED_FIXTURE` from `FAIL`.
